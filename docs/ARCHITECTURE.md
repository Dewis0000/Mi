# Архитектура сайта квест-клуба

> Технический документ по брифу: сайт квест-клуба (сеть квест-комнат) с личным кабинетом, баллами за посещения, онлайн-бронированием, видеотрансляцией из комнат в реальном времени, продажей записей с камер, входом через Яндекс ID / Telegram / MAX / VK ID, админ-панелью и приёмом онлайн-оплаты с фискализацией (касса, 54-ФЗ).
>
> Документ описывает целевую систему целиком — это шаг «продумать», предшествующий кодингу (см. `MASTER_PROMPT.md`, раздел 4, п.1). Реализация разбивается на этапы, см. раздел 14. Все примеры значений (баллы, цены, сроки) — дефолты, не хардкод: в реальной системе это настройки в админ-панели.

## 0. Контекст и подход

Бизнес — клуб квестов: один или несколько физических адресов, в каждом несколько «комнат» (квестов). У каждой комнаты есть видеонаблюдение.

Ключевая установка: сайт должен восприниматься как полноценный многостраничный продукт (каталог, личный кабинет, блог, лояльность, бронирование, трансляции), а не как лендинг с одним скроллом. Карта сайта в разделе 1 — это прямой ответ на требование «не одностраничник».

## 1. Карта сайта (sitemap)

### Публичная часть
- **Главная** — хиро-блок, популярные квесты, баннеры акций, блок «как это работает», отзывы, карта локаций, живой индикатор «Сейчас играют» (см. раздел 7 — без реального видео, только тизер)
- **Квесты** (каталог) — фильтры: город, жанр (хоррор/детектив/sci-fi/семейный), сложность, кол-во игроков, возрастной рейтинг
- **Страница квеста** — описание, фото/тизер, уровень страха/активности, таблица цен, виджет свободных слотов, отзывы, похожие квесты
- **Бронирование/Расписание** — календарная сетка комнат × времени
- **Цены и абонементы** — разовые цены, пакеты, корпоративные тарифы
- **Подарочные сертификаты** — покупка сертификата (код/PDF)
- **Программа лояльности** — правила начисления баллов, уровни, как потратить
- **Для бизнеса** — корпоративы, дни рождения, тимбилдинг
- **Отзывы**
- **О клубе** — локации, команда, правила безопасности
- **Блог/новости** — SEO-контент
- **Контакты** — карта, телефон, мессенджеры
- **FAQ**
- **Публичная оферта / Политика конфиденциальности / Правила посещения** — обязательные юридические страницы (нужны для легальных онлайн-платежей и работы с персональными данными, см. раздел 13)

### Личный кабинет (после входа)
- **Профиль** — данные, аватар, смена телефона/пароля, привязанные соцсети/мессенджеры
- **Мои бронирования** — предстоящие/прошедшие, QR-билет для входа
- **Баллы и история** — баланс, прогресс до уровня, лог начислений/списаний
- **Прямой эфир** — появляется, только если у пользователя сейчас активная сессия (своя или по приглашению) — см. раздел 7
- **Мои видео** — купленные записи + доступные к покупке по прошедшим визитам
- **Сертификаты** — свои подарочные сертификаты, отправка другу
- **Платежи и чеки** — история платежей со ссылками на фискальные чеки
- **Уведомления** — каналы напоминаний (SMS/email/Telegram-бот, см. раздел 3)

### Админ-панель (по ролям, раздел 2)
- Дашборд (сессии на сегодня, выручка, загрузка по комнатам)
- Бронирования (CRUD, календарь, бронирование по телефону, чек-ин на входе)
- Квесты/Комнаты (CRUD, цены, расписание, блок на тех. работы)
- Камеры (статус камер, старт-стоп записи)
- Видео и продажи (список записей, привязка к бронированию, цены, возврат доступа)
- Пользователи (карточка клиента, ручная корректировка баллов, экспорт/удаление данных по 152-ФЗ)
- Лояльность (правила начисления, уровни, множители акций)
- Платежи и чеки (статусы, сверка, возвраты)
- Сертификаты и промокоды
- Контент сайта (лёгкая CMS: тексты квестов, фото, баннеры, блог) — чтобы маркетинг не зависел от разработчиков
- Сотрудники и роли
- Отчёты (посещаемость, выручка, конверсия, когорты по лояльности)
- Журнал доступа к видео (кто смотрел/скачивал съёмку — важно из-за приватности)

Отдельно — **консоль оператора** (см. раздел 10): облегчённый экран для планшета на ресепшене (чек-ин, старт сессии/записи одним тапом), а не полноценная админка.

## 3. Регистрация и вход

### Способы входа
Приоритет для аудитории РФ — сначала соцвход, затем телефон как универсальный фолбэк:

1. **VK ID** — виджет VK ID SDK, даёт имя/аватар, иногда подтверждённый телефон.
2. **Яндекс ID** — стандартный OAuth2 через `oauth.yandex.ru`, даёт имя/аватар/email, по согласию — телефон.
3. **Telegram** — Telegram Login Widget: виджет без редиректа, возвращает подписанный пакет (id, username, имя, фото, `auth_date`, `hash`), подпись проверяется на сервере HMAC по токену бота. Из коробки не даёт телефон/email — только Telegram-идентичность.
4. **MAX** — новый национальный мессенджер/супер-сервис (экосистема VK). На момент написания документа его API/SDK для входа третьих сторон моложе и менее стабилен, чем у VK/Яндекс/Telegram, поэтому: (a) закладываем ту же абстракцию провайдера, чтобы подключить MAX без переделки остальной системы, (b) перед реализацией нужно сверить актуальную документацию MAX по авторизации — она может измениться.
5. **Телефон + SMS-код** — универсальный способ, обязателен как минимум как fallback, потому что телефон — ключевой идентификатор для бронирования и чек-ина на входе (его не всегда отдают соцсети).
6. **Email + пароль** — вторичный способ для тех, кто не хочет соцвход.

### Модель данных входа
- Один `User` может иметь несколько привязанных `ExternalAccount{provider, providerUserId, raw-профиль}` — то есть вход и через VK ID, и через телефон ведут в один и тот же аккаунт.
- Телефон — основной идентификатор. Если соцвход не отдал телефон, после первого входа один раз просим подтвердить его по SMS (нужен для бронирования/напоминаний).
- Если гость бронировал по телефону без регистрации, а потом зарегистрировался тем же номером — прошлые бронирования и причитавшиеся баллы подтягиваются автоматически (matching по телефону).

### Обязательные поля и согласия
- Имя, телефон (обязательно), email (опционально), дата рождения (опционально — для акции «День рождения»), предпочитаемая локация.
- Чекбокс согласия на обработку персональных данных (152-ФЗ, не может быть предзаполнен) и согласия с публичной офертой — обязательны.
- Отдельный чекбокс согласия на видеосъёмку/трансляцию — не при регистрации, а в момент бронирования конкретной сессии (см. раздел 7) — так как это согласие на конкретное событие, а не на аккаунт вообще.

### Безопасность
- Пароли — bcrypt/argon2; восстановление — по SMS-коду или magic-link на email.
- Рейт-лимит и капча (Яндекс SmartCaptcha как более РФ-дружелюбная альтернатива reCAPTCHA) на регистрации/входе/запросе SMS-кода — баллы и бесплатные слоты — ценность, которую боты будут пытаться фармить.
- Опционально passwordless-вход по SMS-коду без пароля вообще — снижает число обращений в поддержку «забыл пароль».

### Побочный эффект входа через Telegram
Если у пользователя привязан Telegram, напоминания о бронировании можно слать через бота бесплатно, а не только платным SMS — стоит сразу предусмотреть `NotificationChannel: SMS | EMAIL | TELEGRAM` в модели уведомлений (раздел 11).

## 5. Программа лояльности и баллы

Требование из брифа: баллы начисляются **за количество посещений**, а не за сумму покупки — визит-ориентированная модель, а не кэшбэк.

- **Триггер начисления**: баллы начисляются, когда бронирование переходит в статус `COMPLETED` (сессия реально состоялась), а не в момент оплаты — иначе баллы получают и те, кто не пришёл.
- **Базовое правило (пример)**: +100 баллов за каждый завершённый визит, независимо от цены квеста.
- **Уровни по количеству визитов (пример)**:

| Уровень | Визитов | Бонус |
|---|---|---|
| Базовый | 1–2 | — |
| Серебро | 3–5 | +10% к начислению |
| Золото | 6–10 | +20% к начислению, приоритетная бронь |
| VIP | 11+ | +30%, бесплатный квест на день рождения |
- **Списание**: баллы можно использовать как оплату части брони (например, не больше 50% от суммы заказа — защита маржи), курс настраивается (1 балл = 1 ₽ по умолчанию).
- **Сгорание**: баллы сгорают через N месяцев неактивности (настраивается) — стандартная защита от бесконечных обязательств.
- **Леджер, а не счётчик**: баланс — это не одно изменяемое число, а неизменяемая таблица проводок `PointsTransaction` (тип: начисление/списание/сгорание/ручная корректировка/реферальный бонус, сумма, связанное бронирование, баланс после операции) — нужно для разбора спорных ситуаций в поддержке.
- Правило начисления сделано как **конфигурируемый движок**, а не хардкод: админ может переключить формулу на «% от суммы» или комбинировать — но дефолт и смысл по брифу — именно количество визитов.
- *Предложение сверх брифа*: реферальная программа «приведи друга» — бонус баллами обеим сторонам после первого визита приглашённого. Явно помечаю как идею, а не требование.

## 6. Бронирование

### Сущности и иерархия
`Локация → Комната/Квест → Слот (комната × дата-время) → Бронирование (слот + клиент + игроки + цена + статус + оплата)`

### Статусы бронирования
```
PENDING_PAYMENT → CONFIRMED → CHECKED_IN → IN_PROGRESS → COMPLETED (→ начисление баллов)
                                                        → NO_SHOW
CONFIRMED/PENDING_PAYMENT → CANCELLED / REFUNDED
```

### Генерация слотов
Менеджер задаёт шаблон недельного расписания на комнату (часы работы, длительность сессии + буфер на уборку/сброс декораций) → система генерирует конкретные слоты на N недель вперёд; ручные правки для праздников/приватных броней/техработ.

### Ценообразование
Базовая цена за слот (будни/вечер/выходные — по-разному), доплата за игрока сверх базового состава, мин/макс игроков, скидки (промокод, баллы, пакет).

### Процесс бронирования клиентом
1. Выбор квеста → выбор даты и времени в календаре → количество и имена игроков (нужно для инструктажа по безопасности) → вход или данные гостя → применение промокода/баллов → оплата → подтверждение (email+SMS/Telegram) с QR-билетом и инструкцией по приезду → напоминания за 24 ч и за 2 ч.
2. **Защита от двойного бронирования**: слот мягко блокируется на 10–15 минут на время оформления оплаты (короткоживущая запись-резерв + уникальное ограничение в БД + джоба истечения) — классическое узкое место систем бронирования, явно проектируем сразу.

### Политика отмены
Настраиваемый порог (например, бесплатная отмена за 24 ч, без возврата при отмене позже 6 ч до сессии) — показывается клиенту на этапе бронирования.

## 7. Прямой эфир с камер

Самая нетривиальная часть брифа технически.

### Оборудование и приём потока
IP-камеры с поддержкой RTSP в каждой комнате, снимающие игровое пространство. На площадке — лёгкий медиа-сервер, конвертирующий RTSP в веб-форматы: рекомендация — **MediaMTX** (бывший rtsp-simple-server) или **go2rtc**, открытые, легковесные, можно держать на мини-ПК на месте и ретранслировать поток в облако, чтобы сайт не зависел от статического IP и NAT на площадке. Альтернатива, если не хочется поднимать своё медиа-железо: управляемые сервисы (Ant Media Cloud, LiveKit Cloud, Cloudflare Stream) — быстрее запустить, но дороже на масштабе.

### Доставка в браузер
HLS (через hls.js) как дефолт — задержка 3–6 секунд некритична для такого сценария («посмотреть, как там наши»), универсальная поддержка. WebRTC — опциональный апгрейд, если понадобится задержка <1 сек.

### Доступ и приватность — важный момент, которого в брифе не было, но без него нельзя
Эфир **не может быть полностью публичным** — в кадре узнаваемые люди (клиенты), это их персональные данные (152-ФЗ трактует изображение как персональные данные).

- На главной/каталоге — только безопасный тизер: индикатор «Сейчас играют: Комната X» со статичной размытой превью-картинкой, без реального видео.
- Реальное видео доступно только тому, кто вошёл в аккаунт **и** привязан к этому конкретному активному бронированию — либо как игрок, либо как «зритель» по ссылке, которую игрок сам отправил родным (короткоживущий подписанный токен, привязанный к id бронирования и комнаты, истекает по завершении сессии).
- При бронировании — явный чекбокс «Я согласен(на) на видеозапись/трансляцию игры» (отдельно от согласия на обработку персональных данных при регистрации). Нужно решить на уровне бизнеса, что происходит при отказе — не снимать вовсе или снимать, но не продавать/не транслировать; оставляю это открытым решением владельца бизнеса, не домысливаю.
- В личном кабинете это вкладка «Прямой эфир» — появляется, только если у пользователя сейчас идёт/скоро активная сессия.
- *Доп. идея*: экран-«стена» в холле клуба с мозаикой всех активных комнат — но без лиц, только название комнаты и таймер прошедшего времени, на основе того же безопасного тизер-потока.

### Хранение
Тот же медиа-сервер пишет сегменты в объектное хранилище S3-совместимого типа — для записи, которую можно купить (раздел 8).

## 8. Покупка записей с камер

- После завершения сессии система автоматически формирует «видео-товар»: обрезка по длительности сессии, бесплатный превью-тизер (первые 20–30 сек, размыто/с водяным знаком) — чтобы заинтересовать купить полную версию.
- Покупка — из вкладки «Мои видео» или по ссылке в SMS/email после визита («Посмотрите, как вы прошли квест — купить видео за 490 ₽»).
- Доступ после покупки — просмотр в личном кабинете (проще в поддержке, чем «скачал и потерял файл») либо скачивание по временной подписанной ссылке.
- **Жизненный цикл хранения**: исходная съёмка автоматически удаляется через N дней (например, 14–30), если не куплена и не помечена как инцидент/материал для разбора безопасности — это и экономит хранилище, и снижает риски по 152-ФЗ (принцип минимизации хранения персональных данных без цели).
- Безопасность доступа: никаких публичных бакетов, только подписанные истекающие ссылки, водяной знак с датой/логотипом против пересылки.

## 9. Оплата и онлайн-касса (54-ФЗ)

Любой платёж от физлица онлайн в РФ требует фискального чека в момент оплаты (54-ФЗ).

### Абстракция
Интерфейс `PaymentProvider` (создать платёж / обработать вебхук / вернуть деньги), чтобы конкретного провайдера можно было поменять без переписывания остальной системы.

| Вариант | Комментарий |
|---|---|
| **ЮKassa (YooKassa)** — рекомендация по умолчанию | эквайринг + чеки + СБП в одном API, самый массовый вариант |
| **CloudPayments** | похожий набор, удобен для рекуррентных платежей (абонементы) |
| **Robokassa** | лёгкая интеграция, агрегирует методы и ОФД |
| Прямая интеграция с ОФД (АТОЛ Онлайн, OrangeData, Platforma OFD) + отдельный эквайринг | больше контроля, больше работы — вариант, если у бизнеса уже есть касса/эквайринг-договор |

### Поток
Клиент платит (бронирование / сертификат / видео) → вебхук провайдера подтверждает оплату → заказ помечается `PAID` → провайдер (или наша интеграция с ОФД) формирует фискальный чек → чек сохраняется и уходит клиенту на email/SMS, виден в личном кабинете и в админке.

### Возвраты
Возврат денег обязательно сопровождается **чеком возврата** — это отдельная сущность `Receipt{type: SALE | REFUND}`, не просто «вернули деньги без документа».

### Безопасность и технические детали
- Номера карт никогда не попадают на наш сервер — только через хостед-виджет/iframe провайдера (вне PCI DSS scope для нас).
- Подпись вебхуков проверяется, статусы платежей меняются идемпотentно, сырые вебхуки логируются для сверки — частый источник реальных багов, если не продумать сразу.
- Тестовый/боевой режим переключается через `.env` — можно строить и проверять весь остальной функционал, не дожидаясь юридического оформления договора с провайдером.

## 12. Технологический стек

Берём стек из `MASTER_PROMPT.md` и добавляем специфику под этот проект:

- **Фреймворк**: Next.js (App Router, TypeScript), Tailwind + shadcn/ui, Framer Motion — как в мастер-промпте.
- **Авторизация**: Auth.js (NextAuth) с провайдерами: credentials (телефон+SMS-код, email+пароль), кастомные провайдеры для VK ID, Яндекс OAuth, Telegram Login Widget, MAX (по готовности его API) — все через единый интерфейс `ExternalAccount`.
- **Данные**: Prisma + MySQL (реальный хостинг — ISPmanager с MySQL, не VPS с PostgreSQL; см. раздел 16).
- **Хранилище видео/файлов**: S3-совместимое объектное хранилище, с оглядкой на резидентность данных РФ (Яндекс Object Storage / VK Cloud Storage / Selectel) — см. раздел 13.
- **Видео с камер**: MediaMTX/go2rtc на площадке (RTSP → HLS), hls.js на фронте.
- **Уведомления**: email (Resend/Nodemailer), SMS (SMS.ru/SMSC.ru или агрегатор), Telegram-бот как бесплатный канал для тех, кто вошёл через Telegram.
- **Фоновые задачи**: генерация слотов, сгорание баллов, напоминания, удаление неоплаченных записей по истечении срока — через очередь (BullMQ) или cron.
- **Формы/данные**: React Hook Form + Zod, TanStack Query, Zustand — как в мастер-промпте.
- **Хостинг**: reg.ru — облачный VPS/VDS (см. раздел 16).

| Этап | Что входит |

## 15. Допущения, принятые по умолчанию

Раз бриф был не в формате полной анкеты из `MASTER_PROMPT.md`, явно фиксирую, что принято по умолчанию (можно поправить — это не окончательные решения, а стартовая точка):

1. Сеть может быть мультилокационной, но для MVP предполагается одна локация с несколькими комнатами.
2. IP-камеры предполагаются как «ещё предстоит закупить/настроить под стриминг» — если что-то уже есть, нужно будет только проверить, поддерживают ли они RTSP.
3. Юрлицо, договор с банком-эквайером и ОФД считаются пока не оформленными — весь платёжный слой проектируется через абстракцию с тестовым режимом, чтобы разработка не стояла в ожидании бумаг.
4. Баллы начисляются за количество визитов (как в брифе), а не за сумму покупки; процент от суммы оставлен опциональным режимом в движке правил, не включён по умолчанию.
5. Хостинг — reg.ru, облачный VPS/VDS, а не бюджетный shared-тариф (см. раздел 16); домен также регистрируется/привязывается через reg.ru. Это заодно хорошо сочетается с ориентацией на РФ-резидентность персональных данных из раздела 13.
6. Интерфейс — на русском языке, мультиязычность не предполагается, но ничего в архитектуре её не блокирует на будущее.
7. Про MAX: закладываем интеграцию на уровне архитектуры (абстракция провайдера), но точную реализацию нужно сверить с актуальной документацией MAX на момент разработки — продукт молодой, API может отличаться от того, что можно предположить сейчас.

## 16. Хостинг и деплой на reg.ru

Провайдер — **reg.ru** (домен и хостинг в одном месте, сервер физически в РФ — само по себе хорошо сочетается с резидентностью персональных данных из раздела 13). Фактически используемый тариф — **обычный хостинг на базе ISPmanager, без root/sudo** (не облачный VPS). БД на этом тарифе — **MySQL**, поэтому Prisma настроен на провайдер `mysql` (`@prisma/adapter-mariadb`), а не PostgreSQL, как в более ранних версиях этого документа.

### Два возможных пути — и как понять, какой у вас

У ISPmanager есть собственный модуль «Node.js» (панель сама ставит нужную версию Node.js и `pm2`, запускает процесс на свободном локальном порту и настраивает Nginx-проксирование на ваш домен). Доступность модуля зависит от тарифа и от того, включена ли для аккаунта опция «Can use Node.js» — это видно в самой панели:

- **Если в ISPmanager есть раздел «Node.js» / «Node.js-приложения»** (обычно в настройках WWW-домена или в «Настройки → Программное обеспечение») — это основной путь, он ниже. Если раздела нет — напишите в поддержку reg.ru с вопросом, включён ли Node.js для вашего тарифа/аккаунта.
- **Если вместо этого вы управляете полноценным VPS с root-доступом** — подходит классическая схема (Nginx + certbot + systemd/PM2, без ограничений ISPmanager); в этом случае используйте `server/ecosystem.config.cjs` напрямую через `pm2` и настройте Nginx/certbot вручную — шаги те же, что в индустрии для любого Node.js-сервера на Ubuntu, здесь не расписаны отдельно.

### Состав (путь через ISPmanager, без root)
- **Node.js** — ставится и управляется самим модулем ISPmanager (версия выбирается в панели; нужна 20 или новее).
- **MySQL** — уже выдан вместе с хостингом (логин/база вида `u1234567_default`, см. личный кабинет reg.ru).
- **Nginx и TLS** — настраиваются самой панелью при создании WWW-домена и Node.js-проекта; отдельно руками ничего не поднимаем.
- **`next build` с `output: "standalone"`** (`next.config.ts`) — собирает автономный `server.js` со всем нужным кодом и минимальным `node_modules`, без которого панели было бы нечего запускать без полной установки зависимостей на сервере.

### Пошаговый чек-лист первого запуска
1. Убедиться, что домен `nery-quest.ru` указывает (A-запись) на IP хостинга — это видно в личном кабинете reg.ru, обычно настраивается автоматически, если домен и хостинг куплены в одном аккаунте.
2. По SSH: `git clone <репозиторий> nery-quest.ru && cd nery-quest.ru`.
3. Создать `.env` по образцу `.env.example`: `DATABASE_URL` с реальными данными MySQL из личного кабинета, `NEXTAUTH_URL`/`NEXT_PUBLIC_APP_URL = https://nery-quest.ru`, секрет `AUTH_SECRET`.
4. Запустить `bash server/install.sh` (при первом разе — с `ADMIN_PHONE="+7..."`, чтобы сразу создать аккаунт администратора). Скрипт делает `npm ci`, прогоняет миграции Prisma, собирает standalone-сборку и копирует в неё статику.
5. В панели ISPmanager — один раз создать Node.js-проект для домена `nery-quest.ru`: корневая директория — `.../nery-quest.ru/.next/standalone`, файл запуска — `server.js`, версия Node.js — 20+.
6. Проверить сайт по домену (все страницы из раздела 1), зайти под админом в `/admin/locations` и указать реальный адрес клуба, добавить квесты в `/admin/rooms`.
7. Настроить регулярные бэкапы БД средствами reg.ru (экспорт MySQL по расписанию — обычно есть в самой панели) и, при появлении видео с камер (разделы 7–8), не хранить записи на том же диске — выносить в отдельное S3-совместимое хранилище (раздел 12).

### Деплой обновлений
Одна и та же команда на каждый релиз:
```
cd ~/nery-quest.ru && git pull && bash server/install.sh
```
После неё — зайти в ISPmanager и нажать «Перезапустить» у Node.js-проекта (панель сама не отслеживает изменение файлов `server.js`, перезапуск — это способ подхватить новую сборку). Если у вас есть прямой доступ к `pm2` по SSH под тем же пользователем, которым владеет процесс, перезапуск можно сделать и из консоли (`pm2 restart quest-club`) — но это зависит от конкретной настройки хостинга, гарантированный способ — кнопка в панели.
